# Signed sync foundation

Unity now pins Foundry's unreleased signed HTTP transport profile and checks its
public `/sync` export in Node ESM, Node CJS and local workerd. The wire/crypto
implementation stays in Foundry. The contract is
[Foundry sync HTTP v1](https://github.com/character-foundry/character-foundry/blob/0e464d69f5722073845954f06c46affb68539eb4/docs/sync-http-v1.md).
Signed publication reads are available behind an explicit HTTPS-only opt-in.
Peer grants require local operator provisioning; migrations grant no access.
Signed publish/fork commands and verified remote-fork bundles have a separate
write opt-in. There is no automatic background sync job.

The audit's unsigned-body example must not be accepted by the new protocol. The
new profile requires a signed SHA-256 body digest, exact target URI/method/media
type, actor and operation ID, an Ed25519 key pinned to that actor, a short validity
window and a fresh nonce. Its verifier requires host-injected atomic nonce
admission before returning verified bytes. It never discovers a key or fetches
a URL. The old ActivityPub/draft-Cavage APIs retain their previous behavior and
are not a fallback for this profile.

`pnpm verify:sync ../.unity-foundry-sdk/packages/character-foundry` exercises the
actual public package. The independent synthetic vector comes from Node crypto,
not from the signing function under test. All three runtimes must reproduce its
exact signature and operation fingerprint, reject tampered bodies, substituted
actors and expired signatures, and consult the replay callback. Foundry has eight
additional focused cases for component tampering, missing/duplicate/extra fields,
algorithm downgrade, noncanonical encoding, clock boundaries, input ownership,
retries, empty GETs and resource limits. `pnpm check` runs the Unity consumer
verification against the pinned, clean external SDK checkout.

The standalone consumer's in-memory nonce set remains a transport test double.
Unity now separately tests the real durable callback on native SQLite and local
D1. Transport admission remains separate from the mutation receipts described below.

## Durable local admission

Store migration 6 adds peers, explicit `pull`/`publish`/`fork` scopes, pinned public
keys and nonces. `@character-unity/store/sync` exports `createSyncStore(driver)`;
Node's `openNodeStore()` also returns `sync`. These are administrative/domain
methods, also used by the [peer operator CLI](peer-operators.md) and the opt-in
read routes below.

- `grant({ actor, accountId, workspaceId, scopes })` binds one exact HTTPS actor
  to an enabled local account and a workspace that account owns. Mapping is
  immutable. `setEnabled` and `setScopes` suspend or reduce access.
- `addKey(actor, keyId, publicKey)` stores only an exportable Ed25519 public key.
  IDs must be fragments of that actor URI. Keys cannot be replaced, deleted or
  unrevoked. Rotation adds a new ID and revokes the old one; no incoming URL is
  fetched. `getPeer` returns the fixed local mapping.
- Bind `resolveKey(actor, keyId, scope)` and `consumeNonce(claim, scope)` to the
  **same host-selected scope** when calling Foundry's verifier. Resolution checks
  current grants; the atomic insertion independently rechecks key, peer, scope,
  account and workspace ownership. Store methods accept only verified SDK claims;
  calling `consumeNonce` alone does not verify a signature.
- Nonces are unique by `(actor, nonce)`, across keys and operation scopes. Only
  an inserted row returns true. Driver failures propagate. Records survive backend
  restart and remain when a key is revoked or an account/peer is disabled.
- `retainUntil` is Unix seconds, including the SDK's skew allowance. The injected
  host clock returns trusted milliseconds. Admission rejects stale or excessively
  distant retention and rechecks time after the database call. `pruneNonces()`
  deletes only records strictly older than the trusted host time; the inclusive
  boundary is retained. Operate with a trustworthy clock, including during cleanup.

Ten shared conformance cases run on each SQL adapter: grants and scopes,
concurrent admission, restart and rotation, revocation between lookup and insertion,
clock/pruning boundaries, failed-batch rollback, actual public SDK verification,
populated v5 upgrade preservation, paginated inspection, atomic rotation and exact-claim read authorization. SQLite concurrency uses separate database
connections; D1 uses overlapping calls to the local binding and a persisted
Miniflare restart. `runtime/sync-conformance.md` is generated by `pnpm test`.

## Opt-in publication reads

Foundry defines the unreleased [read v1 contract](https://github.com/character-foundry/character-foundry/blob/0e464d69f5722073845954f06c46affb68539eb4/docs/sync-read-v1.md)
and exports `createSyncReadClient` from its public `/sync` entry point. Unity mounts
that contract at `/api/sync/v1` when `UNITY_SYNC_ENABLED=true`. Node requires
`UNITY_PROFILE=hub` and an exact HTTPS `UNITY_PUBLIC_ORIGIN`; the Worker requires
an HTTPS origin and `UNITY_SYNC_LIMITER`. The default is `false`; disabled routes
return 404. This flag does not provision peers or grant access.

Every read, including capabilities, requires an Ed25519 signed bodyless GET,
a fresh durable nonce and a current `pull` grant. Requests carrying cookies,
Authorization or Origin headers are rejected. The peer's fixed local account
mapping determines publication visibility. TLS must terminate at the configured
origin; Node may run behind that origin's TLS proxy. Forwarded headers do not
choose the signed URL. Responses rely on HTTPS; they are not independently signed.

| Route below `/api/sync/v1` | Result |
|---|---|
| `/capabilities` | Read version, operations and bounds; no writes advertised |
| `/publications?limit=20&after=ID&parent=ID` | Visible publications, optional direct-fork filter and next cursor |
| `/publications/ID` | Sanitized document, content identity, original-root claim, policy and portable asset manifest |
| `/publications/ID/asset?path=PATH&policyVersion=N` | Exact manifest bytes, only while the expected policy version remains current |

Pages contain at most 20 records in ID order. They are live keyset pages, not an
immutable catalog snapshot. A full last page can return a cursor whose next page
is empty. Documents are bounded to 256 KiB, envelopes to 8 MiB, manifests to 64
assets and each asset to 32 MiB. Internal owner/workspace/revision/source IDs,
storage keys, original downloads and unpublished revisions are excluded.

The public SDK verifies canonical content identity and embedded lineage using
manifest hashes and portable bindings before returning a publication. Asset reads
check length, media type and SHA-256. The original root without lineage remains a
publisher provenance claim, since sanitized publication bytes cannot prove the
accepted original. Redirects, changed response targets, malformed/oversized JSON
and mismatched asset bytes fail. The client has bounded timeouts and cancellation;
it never discovers keys or falls back to browser credentials.

Unity rechecks the exact admitted claim and current grant after domain reads.
Asset downloads also recheck the publication policy before returning their stream.
No-store responses and generic structured failures avoid disclosing internal
records. Node limits admission to 120 attempts per process per 60 seconds; Workers
use the equivalent origin-keyed rate binding, subject to platform consistency
and location scope. These are admission controls, not production abuse guarantees.

HTTP integration tests run the real SDK client against the shared SQLite API and
the bundled Worker with D1/R2. They verify visibility, pagination, exact assets,
opaque fields, unchanged originals, policy conflicts, tamper/replay rejection,
revocation and absence of cookie fallback. A SQLite test revokes a peer during a
read and checks that no document is returned. The ESM/CJS/workerd SDK consumer also
verifies read identity and rejects a modified publication. These tests do not
establish a complete two-instance publish/pull/enriched-return workflow.

## Atomic publish and fork receipts

Migration 7 adds commit-time guards and immutable receipts. The existing shared
hub service accepts an optional **host-only** `SyncWriteContext` on `publish` and
`fork`. The host must obtain the claim from Foundry verification with durable nonce
admission, select the account/workspace from the local grant, and derive the
operation inputs from those exact verified bytes. A context is never accepted from
request JSON. The opt-in command routes below supply this verified context.

The SQL publish and fork operations now support this context directly. Each batch
contains the peer/key/account/scope/workspace check, the exact admitted nonce claim,
a receipt bound to `(actor, requestId, requestHash, operation kind)`, all domain
writes, and removal of the temporary guard. The existing sealed-revision, complete-
asset and publication-fork policy constraints still apply. Sync publication also
checks ancestor visibility at insertion. A grant or source-policy change before
commit aborts the complete transaction.

Receipts contain immutable result references: ordered publication IDs, or the fork's
card/revision IDs. A concurrent duplicate aborts its proposed batch and reads the
winning receipt; no second publication, card or lineage revision is committed.
A lost database response can be recovered with a fresh signed nonce, the same
operation ID and the same operation fingerprint. Other bytes or operation kinds
return `OPERATION_CONFLICT`. IDs are actor-scoped and survive signing-key rotation.

Receipts are not credentials or cached public documents. Returning their results
requires a fresh admitted claim and current grants; fork permission and publication
ancestor visibility are checked again. The service returns the original creation
acknowledgement for publish (IDs and initial policy version 1). Live publication
state is fetched separately. Receipts remain after nonce pruning and cannot be
updated or deleted through the store. No receipt expiry policy is implemented.

`findSyncPublication` and `findSyncFork` provide the service's authorized preflight
lookup. A committed retry skips format preparation and blob copying. The browser
store rejects sync writes; this path requires the shared SQL host.

### Blob preparation and interrupted work

Blob writes finish and are verified before the SQL mutation. SQL references only
ready assets; the receipt commits with those references. There is no successful
receipt for an incomplete upload or failed SQL transaction.

- If SQL committed but the response was lost, a fresh retry reads the receipt and
  returns the same result references without uploading again.
- If an upload or SQL preparation failed before commit, no receipt exists. A fresh
  retry prepares new assets and can complete the operation. Previously staged or
  ready but unlinked objects remain available; they are never deleted speculatively.
- Concurrent first attempts can stage separate blobs before one wins the SQL
  transaction. The losing attempt returns the winner's references. Its unlinked
  objects need the same future operator cleanup as other abandoned uploads.

Automatic cleanup and resumable staging are not implemented. The current recovery
behavior favors retained bytes and an unambiguous SQL result over deleting an
object another operation could still reference.

Nine receipt requirements pass on both SQLite and local D1, including separate-
connection publish races, fork races, restart, lost responses, every SQL batch
failure boundary, key rotation, actor isolation, commit-time grant/policy changes,
protected receipt reads and populated v6 upgrade rollback. The report is
`runtime/sync-operations-conformance.md`. Shared-service tests also use the public
Foundry signer/verifier and actual filesystem blobs to prove retry lineage/byte
stability, skipped copying after commit, and recovery from interrupted upload.
These are application-service/store proofs, not two-instance HTTP protocol proof.

A valid signature is not permission to attribute every embedded lineage author to
the sender. The host must use the versioned command/response contracts below;
transport and domain tests cannot substitute for verifying those routes.

## Opt-in signed publish and fork commands

Set both `UNITY_SYNC_ENABLED=true` and `UNITY_SYNC_WRITES_ENABLED=true` on a Node
HTTPS hub or Worker to enable the [Foundry command v1 contract](https://github.com/character-foundry/character-foundry/blob/0e464d69f5722073845954f06c46affb68539eb4/docs/sync-command-v1.md).
The write flag defaults to false and is invalid without signed reads enabled.
Grant only the needed `publish`/`fork` scopes using the peer CLI. The existing
`createSyncReadApi` composition always remains read-only; hosts that opt into
commands use `createSyncApi` with `writes: true`.

- `POST /api/sync/v1/commands/publish` publishes 1–20 explicitly selected revisions
  already in the granted workspace. It never accepts a workspace/account/author
  from the body and never enables original downloads.
- `POST /api/sync/v1/commands/fork` copies one permitted publication into that
  workspace, with verified public assets and lineage attributed to the locally
  mapped account. Its receipt contains that new private card/revision's IDs.
- `GET /api/sync/v1/command-capabilities` advertises this separate command profile
  when enabled. It uses `pull` scope; a peer with only a command scope can execute
  its configured operation without capability discovery.

The two JSON POST routes bound bytes to 64 KiB, verify the signature and durable nonce
before decoding JSON, require the body operation to match the URL-selected scope,
and pass the exact verified claim into the existing atomic domain operation.
Success returns HTTP 200 with stable creation references. Changed bytes or an
operation kind reusing a receipt ID return 409; source-policy changes during an
operation return 412. Revoked peers, keys, accounts and scopes cannot recover a
receipt. Read and command admission share the host's existing rate limiter.

Foundry's `createSyncCommandClient` requires a caller-generated operation ID from
`createSyncToken()`. Persist the ID and command before sending. After a lost
response, timeout or cancellation, retry those same inputs with a fresh signature;
the operation may already have committed. The SDK never automatically retries,
follows redirects or sends browser cookies. It validates bounded receipts against
the requested operation, ID and result count. A receipt describes creation and
does not replace current policy/identity verification through the read client.

SQLite and actual Worker D1/R2 HTTP tests cover selected publication, verified
assets, mapped fork attribution, lost responses, concurrent duplicate operations,
operation-ID conflicts, key rotation, foreign-workspace rejection, source-policy
revocation, tampered bytes and ambient credentials. A host test revokes a grant
between request verification and the domain call. Public ESM/CJS/workerd consumers
also sign canonical commands and prove retry fingerprints remain stable. The
fresh Node container rehearsal uses real HTTPS for signed read/publish/fork and
recovers the same receipts after container replacement; account suspension then
blocks recovery. The server and SDK client share no browser session credentials.

## Verified remote fork return

The [Foundry fork bundle extension](https://github.com/character-foundry/character-foundry/blob/0e464d69f5722073845954f06c46affb68539eb4/docs/sync-fork-v1.md)
adds `POST /api/sync/v1/commands/submit-fork/PUBLICATION_ID`. It requires the same
write flag and `fork` scope. The SDK's `encodeSyncForkSubmission` and
`createSyncCommandClient().submitFork(bytes, requestId)` produce and sign the
bounded binary frame; Unity does not implement a second codec.

A bundle contains the selected parent ID and content identity, inherited original
root, final document/identity, a linear ancestry proof and all exact asset bytes.
The maximum complete frame is 8 MiB, its canonical metadata 512 KiB, its document
256 KiB, its manifest 64 assets and its intermediate ancestry 32 records. Larger
transfers fail explicitly; resumable/streamed staging remains future work.

Unity looks up the current local parent and fork permission before processing the
bundle. Foundry verifies the final document/lineage and every asset's length/hash.
The first new record must be a fork of that exact source, followed by a connected
chain with no missing, repeated or unproven parents. Every new record's author
must equal the authenticated HTTPS peer actor. Existing parent authors are not
relabeled. Detached record digests prove consistency of the signed claim, not
historical intermediate asset bytes or the truth of the claimed edit times.

Acceptance creates a private draft in the granted workspace and retains the
remote lineage unchanged. The local account remains the responsible store account;
it is not substituted for the remote lineage author. The exact accepted binary
frame is retained as the draft's source, separate from its inherited original-root
hash. Portable asset bindings become Unity revision-asset references. Machine-local
state is rejected. No remote URLs are fetched.

Verified assets finish before the existing atomic fork commit, which rechecks
current grants and parent policy and stores the same two-reference receipt.
Committed retries skip bundle processing/staging; changed payloads reusing the ID
conflict. Receipt recovery still requires current permission. The client must
persist the exact encoded frame and operation ID. Publish the returned revision
only through a separate explicit selection; upload alone never makes it public.

SQLite and actual D1/R2 HTTP tests verify enriched fields and changed asset bytes,
ancestry, source-frame preservation, private-before-publish behavior, concurrent
retries, changed-ID conflicts and source-policy revocation. Correctly signed but
corrupt, disconnected or falsely attributed payloads create no drafts. Both
backends accept a near-limit 8 MiB bundle and return its exact asset hash. The
public SDK consumer verifies bundle submission in ESM, CJS and workerd. The fresh
container rehearsal performs verified pull → remote SDK fork/edit → signed bundle
submission → explicit publication over actual HTTPS, preserves source/asset bytes
and recovers the submission receipt after container replacement.

Unity now also has a [persisted sender service](sync-sender.md): operator-provisioned
HTTPS account actors, explicit remote fork pulls and read-only return preparation
from a selected saved revision. Integration tests use a second persisted Unity
account API and prepare the same bytes after restart, with no network calls.
Existing URN authors are never relabeled. [Durable return jobs](sync-outbox.md) now
persist exact frames, operation IDs, attempts and acknowledgments. Integration
tests recover a lost response after sender restart and peer-key rotation.
The hub now exposes configured connections, explicit pull/return review and retry.
A two-host browser workflow over local HTTPS proves the path through separate
receiving-hub publication with exact assets and retained drafts. A local workerd
sender also passes restart/recovery checks through a harness bridge. See [connected
hubs](remote-hubs.md); deployed peer networking remains unproven.

## Next implementation boundaries

1. **Operator deployment.** Local Node/D1 provisioning, inspection and rotation
   commands are implemented. Remote provisioning/deployment remains separate;
   there is no network key discovery.
2. **Staged-blob operations.** Add operator inspection/cleanup and, if needed,
   resumable staging without deleting referenced or concurrently completing bytes.
3. **Deployment validation.** Local Node browser and workerd sender/receiver
   workflows now pass. Verify public ingress, deployed Worker outbound networking,
   limits and operational recovery on the actual target before enabling peers.
4. **Operator lifecycle.** Connections currently use a protected Node startup file
   or a Worker secret. Key rotation is explicit; private keys remain in the host.
   Operational backup, configuration rollout and staged-blob cleanup remain open.

The foundation is not complete merely because signing succeeds. These application
and interoperability gates remain open, along with remote deployment and Archive
adoption. The public transport contract is a development draft on Foundry's
existing feature branch; no release or merge is implied by Unity's pinned use.
